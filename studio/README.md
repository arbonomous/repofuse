# RepoFuse Studio - demo UI

A local demo UI for RepoFuse: paste two GitHub repos, describe what you want,
and watch the fusion build unfold. Two modes, both honest about what they are.

## Building a selected idea (the build path)

Clicking an idea card starts a real build run: both repos are re-pinned at
the exact commits from the ideas run and re-analyzed (free stages, real),
then three paid synthesis steps - architecture, glue, tests - each gated
exactly like the ideas path (fail-closed envelope.build.json + key,
per-step ONE count-check + ONE charged call ever, durable ledger in
studio/paid-build/, raw retained BEFORE parsing, rejected or indeterminate
attempts recorded durably with their spend state). Generated code is
statically linted (AST) as an accident filter only - NOT a security
boundary: introspection and the vendored dependencies can reach OS,
file and network facilities, and child processes run as the same OS
user, so no path or network denial is claimed from it. The real
boundary is REVIEW: generated code NEVER executes automatically - not
even its own acceptance tests. A build writes its output and STOPS at "awaiting
review": every file the run would execute - generated app,
acceptance tests AND the vendored pinned dependencies - is
pinned by sha256, and the artifacts plus a machine-readable
review request are retained under runs/<id>-build/. Execution
happens only after an independent reviewer approves those exact bytes
via a manifest the build pipeline cannot write (studio/build-
approvals/<run>.json), and the server re-hashes the files at spawn
time, refusing on any mismatch. Approved bytes then run as ordinary
reviewed code under a least-privilege child environment (allowlist
env - the server's own environment, including any model key, is never
inherited - throwaway HOME, cwd in the build dir, 60s acceptance-test
timeout) and are spawned for use on a random loopback port behind a
create/read/delete ownership probe, proxied at
/build/<run-id>/<prefix>. Unregistered, failed or tampered builds
never execute. Residual, stated honestly: approved code has the
normal capabilities of any reviewed app in this repo - it runs as the
same OS user and can read what that user can read; review is the
control, and on the Mac nothing generated runs at all.

Where builds run (the security split):
- Assistant-hosted qualification: freshly generated, still-unreviewed code
  executes ONLY in the disposable assistant sandbox - never on your Mac.
- Your Mac (`git pull` + studio/run.sh): the free stages, the reviewed
  example app, and any build output that has been reviewed and committed.
  Fresh unreviewed generated code is not executed on the Mac.
- The model key stays assistant-hosted in the vault; the Mac never needs
  it for free stages or for running reviewed builds.

First end-to-end build qualification (needs its own fresh specific grant):
3 model calls (architecture, glue, tests) for a selected idea, then the
free verify stage, then open the app and save/edit/delete a row for real.

## Run it (one command, from anywhere)

    studio/run.sh
    # then open http://127.0.0.1:8317/

Equivalent manual form, from the repo root: `python3 studio/serve.py 8317`.

Python 3.10+, stdlib only. Localhost only. No build step, no dependencies,
no API key, no public hosting.

## Mode 1 - Fuse repositories (LIVE, free stages)

Really clones, pins, license-checks and statically analyzes the repos you
paste, right now, using the actual `repofuse` ingest/analyze pipeline.
Then it STOPS: architecture/glue/test synthesis need a model call, and paid
generation is disabled here (no grant, no key). The UI says so, in so many
words. The header badge reads "LIVE - free stages - 0 model calls".

- The recorded repos (microdot, peewee) are pinned to their exact
  qualification commit SHAs; any other repo is pinned to its current HEAD at
  fetch time and the run says that. No unpinned snapshots.
- `git` must be installed and GitHub reachable for this mode.

## Mode 2 - Replay the recorded run (2026-11-04)

Available only when the inputs match the recorded microdot + peewee notes
build (the button disables otherwise; arbitrary inputs are never dressed up
as the recorded run). Replays the real artifacts: the model's ORIGINAL
generated bytes, the real 4/4 acceptance failure, then the assistant's
labeled offline repair (4/4 + vacuity) and edit/delete extension (7/7).
The badge reads "REPLAY - recorded run 2026-11-04". The timeline keeps the
AI stages and the later assistant stages visually distinct.

## Idea suggestions (leave the intent blank)

If you leave "What should it do?" empty, live mode runs the same real
ingest + analyze stages, then `ideas.py` proposes up to three build ideas
from the capabilities it actually detected in the two repos' real exports
(web framework, ORM, auth, templates, realtime, CLI, http client,
validation). Each card cites the exact exports that support it.

This is DETERMINISTIC LOCAL ANALYSIS, not an AI brainstorm - no model
call, no key, no cost, and the UI labels it that way ("SUGGESTED FROM THE
REAL ANALYSIS - local, no model call"). The same idea detection on repos
with no recognized capabilities says honestly that the analysis is too
shallow to propose anything specific.

Picking an idea does not conjure a build:

- "Tiny notes API" on the recorded microdot + peewee pair does NOT start
  anything by itself: it explains that this exact build was recorded on
  2026-11-04 and offers an explicit "Watch the recorded replay" button
  (with a Back-to-ideas escape). The Mode 2 replay starts only from that
  click - picking an idea never silently becomes a new "build".
- Any other card stops at the architecture stage with an explicit
  "needs AI generation - disabled in this demo (no grant, no key)"
  verdict. Turning a picked idea into code is a paid model call and
  stays off until a fresh per-run grant exists.

## Paid idea generation (OFF by default; assistant-hosted qualification)

With the intent blank, Studio first tries the PAID idea path (ideas_ai.py)
and falls back to the free deterministic ideas.py. The paid path activates
only when studio/envelope.ideas.json exists AND validates exactly AND
MODEL_API_KEY / META_API_KEY is present in the process environment. It
ships DISARMED: only envelope.ideas.EXAMPLE.json is included, and arming
is a deliberate per-run act under a fresh user grant.

Grant shape: ONE provider count_tokens check + ONE charged idea-suggest
call for the LIFETIME of the armed envelope. No probe, no retries, no
heal. The strict ledger lives in studio/paid-ideas/ (repofuse.budget,
durable on disk; an interrupted reservation is consumed, never reusable) -
deliberately OUTSIDE the transient per-run workdir, so the single-call
grant survives runs and server restarts. Consuming the grant is permanent
until someone deliberately deletes paid-ideas/ to re-arm under a NEW
grant; the code never resets it. Raw responses and provenance are kept
per run there too (last 10 retained). Concurrency: the whole
count/reserve/call/commit flow runs under an exclusive non-blocking flock
(studio/paid-ideas/idea.lock) plus an in-process thread lock, so a second
server PROCESS or thread refuses before any traffic - one grant stays one
call no matter how many servers are started. A host without flock
(non-POSIX) refuses the paid path outright. The request uses documented
constrained decoding (response_format json_schema) with a DEFINED
{"ideas": [...]} envelope - the exact real qualification failure (a
{"response": [...]} wrapper) and bare arrays both refuse by design. The
raw model response is retained BEFORE parsing; every idea's export
citations are re-verified against the actually observed exports and
unverifiable ideas are discarded. Model cards are labeled
"SUGGESTED BY <model> - 1 paid model call (X in / Y out)"; local cards say
"SUGGESTED FROM THE REAL ANALYSIS - local, no model call". Never blended.
Only export names, pins and license guesses leave the machine - never file
bodies - and the prompt marks repo data as untrusted.

Key handling: process environment only, via the vault write-file pattern
at qualification time, deleted after. Never in the repo, logs, browser, or
chat. No envelope or key ships to the Mac install: the Mac UI stays free
until a supported secure execution path is grounded (no vault/sandbox key
on the Mac is assumed). Picking an idea never starts a build by itself;
paid code generation past idea selection is a separate grant.

Offline tests: `python3 studio/offline_test_ideas_ai.py` - 17 cases over
every fail-closed path (stub transport, REAL budget machinery, no network,
no key, no model).

## The notes preview is the REAL app

The result screen's notes widget talks HTTP to the actual verified example
app (microdot + peewee + SQLite) which `serve.py` starts from
`examples/notes-app-fusion/fused_app` with `assistant_ext` imported, so
edit/delete really register. Verified end-to-end through the proxy:
POST -> 201, GET list/one, PUT edit, DELETE -> 204, 404 on unknown.
If the backend can't start, the panel says so instead of simulating.

## Server hardening (do not remove)

- Binds 127.0.0.1 only; Host header must be this server (DNS-rebinding
  protection); mutating requests with a cross-origin Origin are refused.
- Static serving is an exact allowlist (the 4 UI files). No listing, no
  traversal, no access to runs/, sources, or anything else on disk.
- /api/fuse accepts POST only and only exact
  `https://github.com/<owner>/<repo>` URLs (ingest re-validates and runs git
  with a scrubbed environment). file:, ssh, other hosts, option injection,
  and extra path segments are refused. Cloned code is READ, never executed
  (analyze is pure static: stdlib ast / regex).
- Bounded: 16 KB fuse bodies, 64 KB note bodies, max 2 concurrent runs,
  last 10 runs retained, clones deleted when a run ends, random run ids.
- The notes backend is spawned by this server on a random loopback port and
  must pass a create/read/delete probe handshake before it is proxied; a
  pre-existing service on any port is never trusted.

## Graph vs plan fidelity (do not remove)

The architecture graph is an ILLUSTRATED, assistant-drawn map of the final
repaired app (captioned as such in the UI). The recorded AI's verbatim plan
(raw architecture-manifest.json content, with its original /users routes)
is embedded in replay-data.js as `manifest` and shown raw in the code panel.
Never present the normalized graph as the recorded plan. Version labels show
the pin commit primarily; peewee's 4.5.3 is a source-declared version at a
post-tag pin, not a tag-commit claim.

## Honesty contract (do not remove)

- No live model calls anywhere; no keys; no claim of live paid generation.
- Idea cards are deterministic proposals from the real static analysis,
  never presented as AI output; picking one still stops at the paid
  boundary unless it is the recorded build itself. Model-generated cards
  appear only under an armed per-run envelope, labeled with the model name
  and real token usage - the two sources are never blended or mislabeled.
- The unedited AI output FAILED; the working app is assistant-repaired and
  assistant-extended. Unattended AI fusion is the goal, not yet proven.
- "What's real in this demo?" (top right) states all of this in product.

## Video capture controls

- `?speed=4` - replay at 4x. `?autostart=1` - start replay without clicking.
- `?freeze=<state>` - deterministic still: `ingest`, `analyze`,
  `architecture`, `glue`, `verify`, `extend`, `result`, `notes`, or
  `live&run=<run-id>` (renders a finished live run's real events).

## Files

- `ideas.py` - deterministic idea suggestion from detected capabilities
  (no model calls).
- `ideas_ai.py` - the PAID model idea path (off unless armed per run;
  fails closed on envelope/key/budget/transport/schema guards).
- `envelope.ideas.EXAMPLE.json` - inert template for the minimal grant
  shape; the armed file is never shipped.
- `offline_test_ideas_ai.py` - 17 offline fail-closed tests for ideas_ai.
- `serve.py` - local server: static UI, /api/fuse (real free pipeline),
  /api/run/<id> (real event stream), /notes* (proxy to the real app).
- `index.html`, `styles.css`, `app.js` - the UI (vanilla JS).
- `replay-data.js` - recorded-run dataset generated offline from the
  preserved run artifacts (original AI bytes, repaired bytes, extension,
  architecture plan, telemetry, verdicts). Regenerate only from real run
  evidence, never by hand-editing outcomes.
